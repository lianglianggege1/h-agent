AgentScope Java 记忆体系 · Lesson 0001

Harness 内建 Markdown 记忆 vs Mem0 扩展

同题不同层：一个住在 harness 的 middleware 管线里，一个实现 core 的 SPI

本课目标——学完你能：
  • 说清 Harness 两层记忆的完整流水线（谁抽取、写哪里、怎么合并、怎么注入）；
  • 指出 Mem0LongTermMemory 的接口、挂载点，以及 Harness 为什么没有这个挂载点；
  • 回答核心问题：它们不是同一个机制的两个后端，而是两套平行实现——并说出依据。

1. 一句话结论

两者解决同一个问题：跨会话记住事实，同时防止对话上下文无限膨胀。但它们是两套平行实现：

Harness 内建记忆是 agentscope-harness 的自带子系统——一组 middleware + workspace 里的 Markdown 文件，用你自己配置的模型做抽取和整理。

Mem0 扩展（agentscope-extensions-mem0）是 agentscope-core 定义的 LongTermMemory SPI 的官方实现——一个薄 HTTP 客户端，把抽取和去重外包给 Mem0 服务端。

关键推论：它们互不依赖、互不知晓，甚至可以并存。给 Harness Agent 接 Mem0 不是"换个存储后端"，而是"在同一台 agent 里再叠加一条记忆链路"。

2. Harness 内建记忆：一条文件流水线

两层文件，互不覆盖：第一层 memory/YYYY-MM-DD.md 是每日流水账，只追加、不去重；第二层 MEMORY.md 是周期性 LLM 合并去重的产物，是每轮推理注入 system prompt 的唯一来源。官方文档把这套机制、触发点和后台维护讲得很完整（Harness 记忆文档）。

围绕两层还有三个机制：对话压缩（compaction）、上下文溢出兜底、大工具结果卸载。注意 flushBeforeCompact(true) 正是衔接点——压缩丢掉旧消息之前，先把有价值事实 flush 进日账本，信息才不会随压缩消失。

在你的项目里（backend/.../chat/infrastructure/config/HarnessAgentConfig.java）：三个中文 prompt（flush 抽取、consolidation 合并、compaction 摘要）+ MemoryConfig 全参数装配——flush 节流 30 分钟、consolidation 间隔 30 分钟、上限 4000 token、日账本保留 90 天、会话日志保留 180 天。落盘走 RemoteFilesystemSpec(IsolationScope.USER) → PostgresBaseStore → PostgreSQL workspace_files 表，命名空间 agents/harness-agent/users/{userId}/。

3. Mem0 扩展：core SPI 的官方实现

核心事实：Mem0LongTermMemory 实现的是 io.agentscope.core.memory.LongTermMemory 接口，而这个接口只有两个方法：

Mono<Void>   record(List<Msg> messages)   // 写：把对话交给 Mem0
Mono<String> retrieve(Msg query)         // 读：语义检索，返回注入文本

挂载点在核心层 ReActAgent.Builder：.longTermMemory(memory) + .longTermMemoryMode(mode)（官方 Mem0 集成文档）。模式有三种： AGENT_CONTROL（agent 通过工具自助读写）、STATIC_CONTROL（框架钩子自动往返）、BOTH。

Builder 必填 apiBaseUrl，三个 ID（agentName/userId/runName）至少填一个，检索时按提供字段 AND 精确匹配；metadata 同时影响写入与过滤。它是薄同步 HTTP 客户端：默认 60 秒超时，没有重试、幂等键、断路器——这些都得调用方自己补。

4. 挂载点事实（本地 jar 反编译验证）

问题事实（javap 验证 2.0.1）
HarnessAgent.Builder 有 longTermMemory 吗没有。只有 memory(MemoryConfig)、disableMemoryTools()、disableMemoryHooks()
ReActAgent.Builder 有吗有：longTermMemory / longTermMemoryMode / longTermMemoryAsyncRecord
绕行路径HarnessAgent.Builder.fromAgent(ReActAgent)——先在 core agent 挂 Mem0，再包装成 HarnessAgent
backend 用到这个扩展吗没有。pom.xml 引入了 agentscope-extensions-mem0:2.0.1，但全代码库零引用

验证方式：javap -classpath …agentscope-harness-2.0.1.jar 'io.agentscope.harness.agent.HarnessAgent$Builder'

5. 六维对比

维度Harness 内建 Markdown 记忆Mem0 扩展
抽象层harness 子系统（middleware 管线 + 文件系统），不实现 core SPIcore LongTermMemory SPI 的官方实现
存储形态Markdown 文件（PostgreSQL 行，人可读可改）Mem0 服务端向量库条目
检索方式MEMORY.md 全文注入 + memory_search FTS5 关键词（≤30 条）语义向量 top-k，三层 ID AND 过滤
抽取与去重客户端两段式：flush → 日账本，consolidation → 重写服务端单步 add：Mem0 自己的 LLM 抽取、去重、演化
生命周期治理自动：90 天归档日账本、180 天清会话日志无自动过期，删除/更新全靠 API
失败语义本地 PG 事务写，几乎不失败远程同步 HTTP，60 s 超时，无重试无幂等

顺带一条：隔离模型同构——harness 用 IsolationScope.USER 文件命名空间按用户隔离；mem0 用三层 metadata 过滤。前者天然只有"用户"一个维度，后者有 AGENT/RUN 两级更细的收窄能力。

6. 真要"把 Harness 接到 Mem0"，有两条路线

路线 A：官方扩展（fromAgent 包装）

因为 HarnessAgent.Builder 没有挂载点，得先构建挂了 Mem0LongTermMemory 的 ReActAgent，再用 fromAgent() 包装。代价：Harness 内建记忆默认开启，两条链路会并存双写；薄客户端的失败处理、三层 ID 到业务身份的映射全要自己兜。

路线 B：自建 Gateway（项目走过的路）

历史事实：docs/superpowers/specs/2026-08-23-harness-mem0-memory-design.md 正是"把 Harness 记忆迁到 Mem0"的完整设计（自建 HarnessMemoryRuntime + UserMemoryCatalog + PostgreSQL 控制索引 + outbox）。四天后的 2026-08-27-langchain4j-mem0-long-term-memory-design.md 把它取代——项目不再动 Harness 内建记忆，改为给 LangChain4j 聊天主链路建平行模块。pom 里那个零引用的 mem0 扩展依赖，就是路线 B 时代的遗迹。

取代的核心理由：聊天主链路在 LangChain4j 生命周期里，不在 AgentScope/Harness 生命周期里；平行建模块不动 Harness，风险面小得多。

7. 检索练习

凭记忆作答，别翻上文——检索难度才能换留存。

Mem0LongTermMemory 实现的 LongTermMemory 接口，定义在哪一层？

对。接口是 io.agentscope.core.memory.LongTermMemory，只有 record/retrieve 两方法；harness 的 Markdown 记忆并不实现它。

Harness 记忆的事实抽取与去重发生在哪里？

对。flush 与 consolidation 都用你传给 HarnessAgent 的 model 跑（HarnessAgentConfig 里的中文 prompt）；Mem0 扩展才是服务端抽取。

2.0.1 里直接给 HarnessAgent 挂 Mem0 的障碍是什么？

对。HarnessAgent.Builder 只有 memory(MemoryConfig)；longTermMemory 挂在 ReActAgent.Builder，绕行需 fromAgent() 包装。
