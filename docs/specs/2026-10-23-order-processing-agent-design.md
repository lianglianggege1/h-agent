# 订单处理助手：完整业务链路设计

状态：Q1–Q18 的设计决定已由用户确认，并已完成独立 AgentScope 助手实现。启动与验证见 `docs/verification/order-processing-assistant.md`；实施记录见 `docs/plans/2026-10-23-order-processing-agent.md`。

## 1. 产品目标与范围

新增一个可从现有 Agent 入口选择的独立“订单处理助手”，基于 AgentScope Java 2.0.2 的 HarnessAgent，通过真实 HTTP MCP 调用处理预置订单。在聊天中展示订单、工单、决策卡片，支持正常履约、取消、退货退款和异常处置的完整闭环。

使用者是内部订单运营。订单是主线，工单用于解决阻塞订单的问题。MCP 工具中的商品、支付、仓库、物流规则和初始数据均为模拟实现，但状态变更、持久化、事件处理、用户隔离和幂等真实生效。

范围：已有待处理订单；多商品整单履约；人民币；整单取消、整单退货、全额退还实付金额。暂不包含选品购物车、营销定价、拆单、部分退款、优惠运费分摊、补发、承运商赔付。

每个用户拥有一个长期使用的订单助手，可以在该助手中开启多个聊天；聊天上下文各自独立，订单助手内部共享长期记忆和订单记录。不同用户隔离，同一用户的订单助手与其他 AgentScope 助手隔离。显式重置演示数据只影响当前用户的模拟业务数据。

## 2. 已确认的业务链路

### 2.1 正常履约

已有订单 → 审核信息 → 检查支付 → 检查并锁定库存 → 出库 → 发货 → 等待物流签收 → 完成。

查询不授予变更权限。用户明确要求“处理这笔订单”后，正常流程自动推进；需要额外决策时暂停。等待支付、签收或人工决定是正常业务停点，不属于执行失败，不保持一个 LLM 调用长时间等待。

支付到账、物流恢复、签收等外部事实必须由模拟事件或已有业务记录提供，Agent 不能自行声称它们已经发生。

### 2.2 取消

未发货订单 → 提出取消方案（含释放库存、是否退款、退款金额）→ 用户确认 → 取消并释放占用库存 → 已付款则退款 → 结案。

取消决定一旦生效即禁止后续发货；退款失败保留取消已生效与退款待处理的事实，创建或更新工单并支持重试。方案确认时重新校验发货状态，已发货时旧取消方案失效。

### 2.3 缺货与地址异常

缺货 → 创建关联工单 → 用户选择等待补货或取消退款。补货通过演示事件改变真实模拟库存；重新检查并成功锁库后，才关闭缺货工单并恢复履约。

地址异常 → 创建关联工单 → 用户补充正确地址 → 校验成功 → 关闭工单并恢复履约。备注“已处理”不直接解除任何阻塞。

### 2.4 物流异常

配送停滞 → 创建物流工单。

- 配送恢复：模拟物流恢复事件 → 重新检查 → 关闭工单 → 等待签收。
- 确认丢件：模拟承运方确认丢件 → 提出全额退款方案 → 用户确认 → 执行退款 → 订单与工单结案。

“已联系物流”仅为处理记录，不代表问题已解决。

### 2.5 退货退款

申请售后 → 展示整单退货退款方案 → 用户确认 → 等待退货入库 → 模拟退货入库与验收结果。

- 验收通过：按已确认方案自动退款，成功后关闭售后与关联工单。
- 验收不通过：展示原因，等待人工选择“特批退款”或“拒绝退款并退回商品”。
- 特批退款：显式确认后执行全额退款。
- 退回商品：确认拒绝方案 → 模拟寄回与客户签收 → 关闭售后与工单。
- 退款失败：保持退款未完成，记录失败原因并创建或更新工单；重试成功才结案。

验收是否通过由模拟仓库事实决定，Agent 不能修改验收结论来绕过人工决定。退货库存只能在入库验收规则满足时恢复一次。

## 3. Agent 编排

统一入口 `order-processing-assistant`，注册为独立顶层 AgentScope HarnessAgent，运行类型复用 `HARNESS_STREAMING`。与通用协作助手共用框架、模型客户端和持久化基础设施，各自拥有稳定且不同的逻辑 agentId、提示词、工具集合与工作区。不能仅改变显示名称后复用通用助手身份。

主助手负责理解查询或处理意图、明确订单对象、按状态选择业务协作者、维护订单助手长期记忆并汇总结果。

| 业务协作者 | 责任 | 工具权限方向 |
| --- | --- | --- |
| 订单审核 Agent | 订单信息、支付、库存条件检查，解释阻塞 | 查询、审核与校验 |
| 履约 Agent | 锁库、出库、发货、签收后的完成处理 | 履约工具 |
| 售后与异常 Agent | 工单、取消方案、售后方案、退货退款与恢复 | 工单与售后工具 |

三名业务协作者统一使用 AgentScope 子 Agent，随主助手调用按任务物化；根据业务阶段委托，独立查询可以并行，依赖前置状态的变更顺序执行。不再使用原拟定的 LangChain4j Agentic sequence/conditional 作为订单助手执行引擎。业务规则和状态迁移仍由确定性的 MCP 工具强制校验。

主助手拥有长期记忆管理权；子 Agent 只接收任务所需的订单身份、上下文、授权范围与受限工具，使用独立子会话，不直接改写主助手或其他助手的 MEMORY.md。主助手汇总工具证据与协作结果后提取适合长期保存的事实。

对用户保留一个聊天入口，进度中可展开查看协作者、阶段、工具摘要与结果。无需用户分别进入三个协作者聊天。

### 3.1 用户、助手与聊天的隔离

第一版每个用户只有一个订单助手，`(userId, order-processing-assistant)` 是用户私有助手的逻辑身份；并不要求为每个用户永久常驻一个 Java 对象。共享定义与无状态基础设施可以复用，每轮必须绑定真实用户与会话，从持久化存储恢复相应状态。

| 对象 | 身份与隔离规则 |
| --- | --- |
| 运行类型 | HARNESS_STREAMING 可被多个独立助手复用，不作为助手身份 |
| 助手定义 | 稳定 agentId；订单助手与通用协作助手不同 |
| 用户私有助手 | userId + agentId；拥有自己的长期记忆、工作区、工具与配置 |
| 聊天会话 | 全局唯一 sessionId，服务端绑定 userId + agentId；不同助手不复用同一会话身份 |
| 子会话 | 独立 sessionId，绑定实际根订单助手及父会话 |
| 业务数据 | 按可信 userId 隔离；订单与操作记录跨该用户的订单聊天一致 |

已核实安装版 SDK 的 USER 远程工作区命名空间含 `[agents, agentId, users, userId, route]`，不同 agentId 已能隔离远程记忆、skills 和 plans；无需仅为此重复包装 BaseStore。订单助手仍配置独立物理 workspace 模板路径，避免模板、本地 fallback 和默认配置混用，不继承通用助手的共享路径声明。

核心 AgentStateStore 的槽位按 `(userId, sessionId, agent_state)` 定位，不包含 agentId。沿用产品全局唯一且绑定单一助手的 sessionId；禁止为了“同一个订单”让不同助手复用 sessionId。订单身份和聊天身份不是同一个东西。

### 3.2 三类历史与记忆

- 会话状态：当前聊天消息、工具上下文、压缩摘要及权限等可恢复状态，按会话保存。
- 助手长期记忆：处理偏好、稳定事实、历史摘要与检索线索，保存在该用户订单助手的专属空间，跨订单助手聊天共享，不自动读取通用助手记忆。
- 业务操作记录：完整持久化记录审核、库存、发货、决定、退款等操作及实际结果，由 MCP 查询，不能靠 LLM 抽取或 MEMORY.md 代替。

“历史操作可查回”是业务保证；“全部历史永远在模型当前上下文中”不是目标。执行前始终查询最新业务状态，不能凭记忆中的“已退款”判断是否继续。订单助手的历史检索也必须过滤用户和助手，不因提供 session_search 等能力而读取其他助手的聊天。

当前通用 Harness 会压缩上下文，记忆提取和整理存在节流，记忆文件也有保留期；订单业务操作记录不继承这些记忆清理策略。订单助手采用隔离的 Markdown 记忆链路，默认不接公共 Mem0 USER scope。

重置演示数据不删除聊天和通用用户偏好，但必须使旧业务代次关联的记忆摘要失效或标注为旧演示记录，不能把旧订单事件当作重置后的事实。

## 4. 模块分工与权威状态

### other-agents：模拟业务模块与 MCP 服务端

拥有订单、商品行、支付、库存占用、物流、售后、退款、工单、业务方案、命令回执和业务变更记录。预置数据按用户初始化；服务重启不重置。

对外使用一个独立订单 MCP 工具组。查询、业务变更和模拟外部事件都进入同一个业务模块，集中处理状态前置条件、金额、库存一致性、方案权限、并发与幂等。

演示事件与重置能力仅供认证后的演示操作入口调用，不进入 LLM 可见工具列表。普通 Agent 无法自己模拟支付成功、验收通过或物流签收。

持久化采用独立 `order_demo` schema 和独立迁移历史，由 other-agents 拥有，避免两个服务争用当前默认 Flyway 历史表。backend 不直接修改该 schema 的业务记录。

### backend：独立 AgentScope 助手、运行协调与聊天投影

拥有用户与会话授权、AgentScope 主子 Agent 编排、助手记忆与工作区隔离、执行请求、恢复任务、事件触发记录、聊天消息和卡片快照。通过真实 MCP 调用业务模块，不在 backend 另建一套订单状态。

新增统一订单处理入口，接收用户请求、卡片决定和演示事件。所有入口检查用户、订单、方案和来源会话，生成持久化执行请求；每次执行从 MCP 获取最新业务状态。

复用现有 Harness 执行、事件和会话持久化适配器，并将审批恢复、协作寻址、子会话摘要与记忆管理中固定指向通用协作助手的逻辑，改为根据实际会话绑定的根助手与能力解析。仅新增第二个 HarnessAgent Bean 不足以实现完整隔离。

业务方案确认与 SDK 工具批准分开：前者校验取消/退款等业务授权、金额和版本，后者执行平台工具权限策略。两种恢复路径都必须定位实际订单助手，不能回退到通用协作助手。普通处理授权不能被 SDK 的宽松工具模式扩展为退款授权。

等待外部事件的流程使用持久化业务状态与后续 AgentScope 运行继续，保持原订单、处理身份和来源聊天。SDK 会话恢复帮助找回对话状态，但不能替代业务事件消费、执行任务恢复或副作用幂等。

### frontend：卡片与演示入口

在既有 `activityRenderers` 上增加订单、工单与订单决策卡片。动作提交结构化业务命令，服务端使用白名单解析；浏览器不能提供任意工具名并要求执行。

## 5. MCP 工具的建议接口

以下是职责分组，具体名称可在实现中统一；避免一个允许任意状态值的 `update_order` 工具。

| 分组 | 建议工具能力 |
| --- | --- |
| 查询 | 列举演示订单、订单详情、处理轨迹、关联工单与待决策方案 |
| 审核 | 校验订单、支付和库存条件，提交审核结果 |
| 履约 | 锁定库存、出库、发货、基于签收事实完成订单 |
| 决策 | 创建业务方案、读取方案、确认或拒绝方案 |
| 工单 | 创建/更新工单、记录处理说明、重新校验并尝试解决 |
| 售后 | 申请退货、按已授权方案取消/退款/拒绝售后、重试失败退款 |
| 演示操作 | 支付到账、补货、物流停滞/恢复/丢件/签收、退货入库验收、退回商品寄送/签收、退款失败注入、重置 |

查询结果和命令结果使用结构化业务对象，包含业务 ID、revision、状态、阻塞原因、可执行动作、关联工单/方案和必要摘要。卡片适配器消费明确类型的结果，不解析自由文本判断“发货成功”。

业务写入命令包含稳定命令 ID、目标业务身份和期望版本。退款金额由订单与已确认方案计算；模型不能自由指定应退金额。退款重试复用同一业务退款身份。

服务端可信调用上下文承载 userId、根助手 agentId、实际 sessionId、来源 sessionId 和运行身份；不得由模型工具参数提供身份。订单 Harness 的 MCP 集成从 AgentScope RuntimeContext 注入并传播这些身份，当前运行的主/子 Agent 仅能看到其允许的业务工具。客户端与 middleware 不在共享可变字段保存“当前用户”。

在服务 Bearer 之外增加必填业务身份传播，独立于可关闭的观测 baggage。现有 LangChain4j MCP 客户端可作为传输和观测参考，但不直接把 McpToolProvider 当作 AgentScope Toolkit；订单 MCP 适配器需适配 AgentScope 当前版本的工具与运行上下文。若复用公共传输包装层，必须保留完整调用上下文。

## 6. 状态与一致性

分别记录履约、支付退款、售后和工单状态，展示时组合成易懂的订单状态，避免一个字符串同时承担所有生命周期。

- 履约：待审核、待支付、待履约、待出库、待发货、已发货、已签收、已完成、已取消、丢件结案等阶段。
- 支付退款：未支付、已支付、退款待执行、退款失败、已退款。
- 售后：无售后、待方案确认、待退货、待验收、待人工决定、退款中、待寄回、待客户签收、已结案。
- 工单：待处理、处理中、等待外部条件、等待人工决定、已解决。
- 业务方案：待确认、已确认、已拒绝、因状态变化失效。

这是实现用的状态分解建议；以已确认的业务链路为验收依据。

每个用户、每个订单串行推进状态变更。业务 revision 与事务控制处理多聊天竞争；同一阻塞只创建一个活跃工单。库存占用、出库扣减、取消释放和退货回补均使用可验证的业务身份，保证不会重复扣还。

支付、签收、入库等事件具有稳定事件 ID，重复投递不重复生效；不满足前置条件的事件明确拒绝或等待其前置事实，不无条件跳状态。

方案固定用户、订单、动作、金额、条件和授权范围。确认时重新校验；条件仍有效才生效。成功或失效的旧卡片不能再次执行。普通处理授权不等于允许取消、退款或特批。

已成功的业务动作不因浏览器停止、运行中断或后续失败而撤销；需要补偿时创建明确的补偿命令。取消和退款等多步业务保留部分完成事实，恢复时从未完成步骤继续。

## 7. 卡片与聊天交互

| 卡片 | 默认信息 | 交互 |
| --- | --- | --- |
| 订单 | 商品摘要、编号、实付、当前阶段、阻塞与下一步 | 查看详情、处理订单、引用到输入框；按状态显示可用动作 |
| 工单 | 问题、编号、关联订单、负责人、状态、解除条件 | 查看详情、补充信息、选择处理方案、重新检查 |
| 决策 | 具体操作、原因、金额或条件、影响范围 | 确认、拒绝；提交中禁重复，完成后展示结果 |

卡片适配既有 448px 窄版布局。详情可展开，默认保留少量关键字段。助手查询后可直接返回卡片；输入框加号支持选择并引用订单/工单，引用传递稳定业务身份。

业务操作成功后更新本聊天中的对应卡片，并补充简短结果消息。失败在卡片中展示可理解原因与适用的重试操作。加载历史或跨聊天重新观察时，以最新业务状态更新展示并标注更新时间；操作记录和已处理方案保留当时事实。

卡片 ID 在会话内稳定，以会话、实体类型和业务 ID 定位。底层业务 ID 跨聊天一致，不能因另一个聊天展示同一订单而把一张卡片跨会话搬移。快照是展示投影，点击动作始终重新验证业务事实。

演示控制区明确标为“模拟外部事件”，展示当前适用的事件入口。重置前展示当前用户范围，确认后切换演示数据代次，使旧命令、旧事件和旧待确认方案失效；历史消息保留并标注演示数据已重置。

## 8. 确认、事件与重启恢复

卡片决定和演示事件先记录持久化请求，再调用 MCP。业务变更与命令回执在业务模块同一事务生效。即使响应丢失，使用相同命令 ID 查询或重试也不会再次执行。

事件或决定生效后创建可恢复的后续执行请求，向原来源聊天追加卡片与结果。每个处理实例记住来源聊天；其他聊天可查询最新状态，不把自动续跑结果任意写到无关聊天。

恢复请求持久绑定 userId、实际根订单助手 agentId、来源 sessionId、业务处理与命令身份；重建 AgentScope 运行时按这些身份恢复状态，不能只按 HARNESS_STREAMING 类型获取默认通用助手。会话级并发协调避免同一对话被两个运行同时写入，订单级并发协调避免两个聊天重复推进同一订单。

业务请求、运行任务和卡片投影分别可恢复：若业务提交成功但聊天更新前进程退出，恢复后凭回执与最新业务状态补齐投影，而不是重做发货/退款。

backend 重启后扫描未完成任务，使用执行租约/并发控制恢复已授权步骤。等待人工决定继续等待；等待外部事件继续等待。工具不可用等技术故障采用有限重试并显示失败原因，不让 Agent 无限循环。

业务阻塞（缺货、地址异常等）进入对应工单分支；纯技术故障不会被伪装成支付失败、物流丢件等业务事实。观察连接只恢复展示，不重新提交已接受的命令。

## 9. 演示数据与验收

预置六类主场景，分支通过演示事件选择，支持显式重置后重复验证。

1. 正常订单：审核到发货；模拟签收后自动完成。
2. 待支付：处理停在等待支付；模拟支付成功后继续，重复支付事件不重复生效。
3. 缺货：工单等待；补货后重新锁库继续，或确认取消退款；备注不能直接关单。
4. 地址异常：补充并验证地址后工单解决，订单继续。
5. 物流异常：恢复配送后正常签收；或确认丢件后经退款方案确认结案。
6. 售后：验收通过退款；验收不通过后特批退款或退回商品；失败退款可安全重试。

额外必须验证：未发货取消与库存释放、未付款禁止发货、同订单两个聊天并发处理、重复确认、失效方案、重复/乱序事件、断线观察、服务重启、MCP 响应丢失、业务成功但聊天投影尚未写入、用户隔离、演示重置后的旧动作失效。

助手隔离必须验证：同用户订单助手和通用协作助手的记忆/工作区/工具不串用；同类 Harness 不同逻辑 agentId 可以并存；同一订单助手新聊天不混入旧聊天完整上下文但能检索自身长期记忆和业务记录；不同用户同名助手隔离；子 Agent 无权改写其他记忆；审批/拒绝/停止/重连/重启都回到实际根助手；关闭观测后 MCP 身份隔离仍生效；压缩或清理记忆不删除业务操作记录。

测试分层：业务命令和状态迁移测试；真实 MCP 协议与身份隔离测试；AgentScope 主子 Agent 编排和记忆隔离测试；AG-UI 卡片与恢复测试。模拟数据不代表可以只测固定成功返回值。
