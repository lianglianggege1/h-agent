# 文档能力需求说明：解析 · OCR · Jev 复核 · 生成

- 日期：2026-11-04
- 状态：需求确认中（未开始编码）
- 范围：通用助手（`STANDARD_STREAMING_CHAT`）与协作 Agent（`HARNESS_STREAMING`）
- 说明：文中的「协助 Agent」按协作 Agent（`harness-agent`）理解，不包括租车应急协助 Agent；后者如需接入，复用同一套应用服务即可。

## 1. 目标

当前仓库只在知识库入库链路中使用了 Apache Tika（`KnowledgeIngestServiceImpl`），通用对话 Agent 不具备读取用户文档的能力；上传接口也只放行图片、音视频。用户希望把文档能力变成 Agent 的一等工具：

- 能读：解析用户上传的任意文件，理解内容后与用户对话。
- 能判断：识别结果不可靠时，知道何时该升级到 OCR，并知道结果是否可信。
- 能复核：OCR 结果必须经过 Jev 质量判断，低分内容由用户拍板。
- 能改写：按用户指令修改、优化内容，并生成新的文件。
- 双运行时一致：通用助手与协作 Agent 能力对等。

设计原则：给 Agent 最大的权限、最全的数据、最完整的流程知识，让它能独立完成从「读文件」到「交付新文件」的闭环；工程上只保留必要的超时、重试与安全边界。

## 2. 范围

### 2.1 包含

- 聊天附件上传文档与任意文件（含 HTML）。
- 本地文档解析工具 `parse_document`。
- 基于 ModelBest 官方 `document-parse` API 的 OCR 工具 `ocr_document`。
- 基于 ModelBest 官方 Jev API 的强制质量复核 `verify_ocr`。
- 低分结果的用户确认流程（前端确认卡 + 后端状态约束）。
- 文档生成工具 `generate_document`，支持新建与基于原文件改写。
- 两个运行时的工具注册与流程知识注入。
- 前端附件、解析状态、确认卡、生成文件卡。

### 2.2 不包含

- 本地部署 OCR / Jev 模型，或引入 GPU 依赖。
- 知识库入库链路改造。
- 文档内容的向量化、检索增强。
- 对扫描件做版式级像素还原。

## 3. 端到端流程

```
用户上传文件（任意类型，含 HTML）
  → 资源入库，记录原文件名 / 扩展名 / MIME / 大小
  → parse_document（本地 Tika）
       ├─ GOOD  → 直接把正文与结构交给 Agent
       └─ LOW / EMPTY → ocr_document（ModelBest document-parse）
                          → verify_ocr（Jev，强制，不可跳过）
                               ├─ 全部块 ≥ 阈值 → 标记已复核，继续
                               └─ 存在低分块 → 挂起，等用户确认
       用户确认「继续使用」→ 标记人工确认，继续
       用户选择「重新识别」→ 带提示重新 OCR 并再次复核
       用户选择「人工修正」→ 接受用户提供的修订文本后继续
  → 用户提出修改 / 优化 → generate_document → 新文件写入会话并投递到聊天
```

约束：任何依赖 OCR 内容的下游动作（生成文件、给出结论、写入长期记忆）都必须发生在其 Jev 复核通过或用户确认之后。
