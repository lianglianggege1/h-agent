# Chat Guardrail Blocked Message 设计

## 背景

当前聊天流里，`InputGuardrail` 审核不通过时会被当成普通错误处理。这样会导致两个问题：

1. 前端会同时看到拦截类提示和系统兜底错误，语义混乱。
2. 平台拦截被当成故障，用户无法明确区分“内容被平台拒绝”和“服务真的失败”。

本需求希望把“平台拦截”作为一种独立结果展示在聊天气泡里，并且保留到会话历史中。

## 目标

1. 将守护拦截结果从普通 error 中分离出来。
2. 在聊天流中新增 `blocked` 消息类型，展示为平台拦截气泡。
3. `blocked` 消息需要写入会话历史，刷新后仍可回显。
4. 真正的运行错误继续走现有 error 兜底逻辑，不影响现有错误提示。

## 非目标

1. 不修改 `InputGuardrail` 的校验规则本身。
2. 不把完整 runtime loop 写入聊天消息历史。
3. 不新增独立的运行事件表。
4. 不改变现有用户消息与 assistant 正常回复的历史展示方式。

## 设计决策

### 1. 引入独立的 blocked 语义

平台拦截不再被视为普通错误，而是一个独立结果类型：`blocked`。

建议的流式事件语义如下：

- `chunk`：正常流式输出片段
- `done`：正常完成
- `blocked`：平台拦截，表示输入被守护规则拒绝
- `error`：真正的系统或模型异常

### 2. 后端直接区分 blocked 与 error

后端需要在聊天流输出阶段把守护拦截单独识别出来，不再落入通用的 `BusinessException(50003, "AI 服务调用失败")` 路径。

对于守护失败：

- 保留原始拦截文案
- 写出 `blocked` 事件
- 不触发“暂时无法响应，请稍后重试”的兜底内容

对于真正的系统错误：

- 继续使用现有 `error` 事件
- 继续保留兜底错误展示

### 3. 历史记录保存 blocked 消息

`blocked` 消息要作为会话中的正式消息保存，而不是临时 UI 状态。

保存后要求：

- 当前会话可以看到该条拦截消息
- 打开历史会话后可以再次回显
- 消息列表中可以区分 `assistant` 和 `blocked`

### 4. 前端使用独立渲染样式

前端需要为 `blocked` 增加独立消息样式，表现为“平台安全拦截”卡片，而不是红色错误文本。

推荐视觉表达：

- 左侧对齐，和 assistant 同侧
- 颜色使用浅橙/浅黄系
- 标题使用“平台安全拦截”
- 内容展示守护给出的原始原因

### 5. 兜底错误保持不变

真正的错误仍然维持现有体验：

- 流式请求失败时显示错误提示
- assistant 占位气泡可以展示“暂时无法响应，请稍后重试”

这样平台拦截和系统错误就不会混在一起。

## 数据流

### 正常回复

1. 用户发送消息。
2. 后端写入用户消息。
3. 后端执行 agent 流式回复。
4. 后端写入 assistant 最终回复。
5. 前端展示正常对话气泡。

### 平台拦截

1. 用户发送消息。
2. 后端守护校验失败。
3. 后端识别为 blocked 场景。
4. 后端输出 `blocked` 事件。
5. 前端渲染平台拦截卡片。
6. blocked 内容写入历史记录。

### 真正错误

1. 用户发送消息。
2. 后端发生模型、网络或运行时异常。
3. 后端输出 `error` 事件。
4. 前端继续显示现有错误提示与兜底文案。

## 后端改动范围

需要关注的文件：

- `backend/src/main/java/com/h/backend/chat/service/impl/ChatServiceImpl.java`
- `backend/src/main/java/com/h/backend/chat/controller/ChatController.java`
- `backend/src/main/java/com/h/backend/chat/service/impl/ChatSessionServiceImpl.java`
- 相关测试文件

后端职责拆分如下：

1. `ChatServiceImpl`
   - 负责识别守护失败与普通错误的差异。
   - 负责把 blocked 结果转成可传递给控制器的业务语义。
2. `ChatController`
   - 负责把业务语义写成 NDJSON 流事件。
   - 负责区分 `blocked` 与 `error` 的输出。
3. `ChatSessionServiceImpl`
   - 负责把 blocked 消息作为正式会话消息写入与读取。

## 前端改动范围

需要关注的文件：

- `frontend/app/chat/page.tsx`
- `frontend/lib/http.ts`

前端职责拆分如下：

1. `apiStream`
   - 解析 `blocked` 流式事件。
   - 把它交给上层回调。
2. `ChatPage`
   - 新增 `blocked` 消息类型。
   - 渲染平台拦截气泡。
   - 保留 error 的兜底处理。

## 消息模型

前端聊天消息类型需要支持：

- `user`
- `assistant`
- `blocked`

其中 `blocked` 与 `assistant` 同属左侧消息，但视觉表现不同。

后端历史消息读取时也要能恢复这一语义，避免被归并成普通 assistant 消息。

## 错误处理

### 1. 守护拦截

守护拦截不应再被包装成“AI 服务调用失败”。

目标行为：

- 显示平台拦截消息
- 不触发红色系统错误提示
- 不让兜底文案抢占用户注意力

### 2. 普通运行错误

普通运行错误仍按现有方式处理。

目标行为：

- 保留 error 流事件
- 保留前端错误提示
- 保留“暂时无法响应，请稍后重试”兜底

## 测试策略

### 后端测试

1. 守护拦截测试
   - 验证输入守护失败时不会被转换成普通 AI 服务失败。
   - 验证 blocked 语义能被单独识别。

2. 会话持久化测试
   - 验证 blocked 消息能写入会话历史。
   - 验证读取历史时可以恢复 `blocked` 角色。

3. 普通错误回归测试
   - 验证非守护异常仍走 error 兜底。

### 前端测试

1. blocked 消息渲染测试
   - 验证 `blocked` 事件会被解析为独立消息。
   - 验证 UI 使用平台拦截样式，而不是红色错误样式。

2. 错误回归测试
   - 验证普通 `error` 事件仍显示现有兜底提示。

## 成功标准

满足以下条件即认为设计目标完成：

1. 输入守护不通过时，前端显示平台拦截气泡。
2. 前端不会同时出现平台拦截与普通错误兜底两种提示。
3. blocked 消息会进入会话历史并可回显。
4. 普通系统错误仍保持现有错误处理方式。
5. 整个链路的语义清晰，不再把“内容被拦截”和“系统故障”混为一谈。
