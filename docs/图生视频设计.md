# 图生视频设计

## 1. 背景

项目已经具备完整的 MiniMax 文生视频异步任务链路：

1. Agent 调用 `text_to_video` 工具。
2. 提交 MiniMax 视频生成任务。
3. 持久化本地生成任务。
4. 定时轮询供应商任务状态。
5. 下载生成的 MP4 并保存为聊天资源。
6. 更新当前聊天中的 pending 消息。

图生视频与文生视频使用同一组 MiniMax 任务提交、状态查询和文件下载 API，主要差异是图生视频必须提供 `first_frame_image`。

本设计的目标是在保持现有文生视频运行语义的前提下，增加图生视频能力，并抽取图生图与图生视频的参考图片解析逻辑。

## 2. 设计目标

- 支持使用新上传图片生成视频。
- 支持使用历史聊天中的用户图片或 AI 生成图片生成视频。
- 图生图与图生视频使用相同的 `referenceResourceId` 选图语义。
- 参考图片的所有权校验、类型校验和内容读取只实现一次。
- 复用文生视频的任务轮询、下载、存储和聊天回显链路。
- 保留文生视频与图生视频各自明确的业务入口和参数约束。
- 避免把 Base64 图片写入任务表。

## 3. 非目标

- 本期不实现首帧和尾帧双图生成。
- 本期不实现 MiniMax callback，继续使用现有定时轮询机制。
- 本期不让模型根据“历史第几张图”自行猜测资源 ID。前端选中哪张图，就将对应的 `referenceResourceId` 传入当前请求。
- 本期不重写前端视频展示组件。

## 4. 总体方案

采用“两个独立业务入口，三个共享能力”的设计。

### 4.1 独立业务入口

- 文生视频：`TextToVideoTool` -> `SubmitTextToVideoUseCase`
- 图生视频：`ImageToVideoTool` -> `SubmitImageToVideoUseCase`

两个入口不合并成一个带大量可空参数的接口。图生视频必须在类型上明确要求 `referenceResourceId`，防止将“文生视频”与“图生视频漏传图片”混为同一种情况。

### 4.2 共享能力

1. 图生图与图生视频共享参考图片解析。
2. 文生视频与图生视频共享 MiniMax 视频 HTTP 客户端。
3. 文生视频与图生视频共享本地任务状态流转、轮询、下载、存储和聊天投影。

```text
                        ReferenceImageResolver
                       /                      \
                  图生图                    图生视频
                                                    \
                                                     MiniMaxVideoClient
                                                    /
                  文生视频 -----------------------
                                  |
                         GenerationTask 通用链路
                                  |
                      轮询 -> 下载 -> 聊天回显
```

## 5. 参考图片解析模块

### 5.1 职责

新增共享的 `ReferenceImageResolver`，统一负责：

- 根据 `resourceId` 查询 `chat_message_resources`。
- 校验资源存在且属于当前用户。
- 校验资源类型为 `IMAGE`。
- 根据 `storageKey` 从 `ResourceStorage` 读取图片。
- 返回图片内容、MIME、大小和尺寸等统一信息。

参考图片不限制为本轮上传或当前会话产生的图片。只要前端或 Agent 提供明确的 `referenceResourceId`，且资源属于当前用户，即可使用。这与现有图生图语义保持一致。

### 5.2 接口设计

```java
public interface ReferenceImageResolver {
    ResolvedReferenceImage resolve(Long userId, String resourceId);
}
```

```java
public record ResolvedReferenceImage(
        String resourceId,
        String mimeType,
        byte[] content,
        long fileSize,
        Integer width,
        Integer height
) {
}
```

### 5.3 Data URL 转换

参考图片解析模块不直接绑定 MiniMax 协议。Data URL 转换由独立的无状态编码器负责：

```java
public final class ImageDataUrlEncoder {
    public static String encode(ResolvedReferenceImage image) {
        return "data:" + image.mimeType() + ";base64,"
                + Base64.getEncoder().encodeToString(image.content());
    }
}
```

图生图的 `subject_reference.image` 和图生视频的 `first_frame_image` 共享该编码器。

Base64 只在调用供应商 API 时临时生成，不写入 `generation_tasks.spec_json`。

### 5.4 校验边界

`ReferenceImageResolver` 只执行所有使用场景共有的安全校验和资源读取。

MiniMax 图生视频的特有限制由 `ImageToVideoSourceValidator` 处理：

- 格式为 JPG、JPEG、PNG 或 WebP。
- 文件小于 20MB。
- 图片短边大于 300px。
- 长宽比在 `2:5` 到 `5:2` 之间。

不将这些限制放入公共解析器，避免图生图和图生视频的供应商规则相互影响。

## 6. Agent 工具路由

### 6.1 图生视频工具

新增 `ImageToVideoTool`：

```java
public String imageToVideo(
        @ToolMemoryId String memoryId,
        String referenceResourceId,
        String prompt,
        String originalPrompt,
        String model,
        Integer durationSeconds,
        String resolution,
        Boolean promptOptimizer,
        Boolean fastPretreatment,
        Boolean aigcWatermark
)
```

工具描述必须明确输出媒介边界：

- `generateImage`：生成或修改静态图片，包括重绘、换风格、换背景等。
- `image_to_video`：让参考图片中的主体或环境运动，或产生运镜、动画和视频。
- 仅分析或描述图片：不调用生成工具。
- 用户的目标媒介无法确定时：询问用户需要静态图片还是视频。

语义判断由模型根据用户请求完成，Java 代码不维护“动起来”、“换背景”等关键词规则。

### 6.2 参考图片上下文

当用户上传图片或在历史聊天中选中图片时，当前聊天请求将该资源作为 `REFERENCE` 传入。`HAssistantStreamingExecutor` 向模型追加上下文：

```text
用户选择了一张参考图片，资源 ID 为 xxx。

根据用户目标选择工具：
- 生成或修改静态图片：调用 generateImage。
- 基于该图片生成动态视频：调用 image_to_video。
- 仅分析或描述图片：不调用生成工具。

调用图片或视频生成工具时，将 xxx 作为 referenceResourceId。
```

## 7. 应用层设计

### 7.1 独立用例

新增：

- `SubmitImageToVideoCommand`
- `SubmitImageToVideoUseCase`
- `SubmitImageToVideoService`
- `ImageToVideoSubmissionPort`

`SubmitImageToVideoService` 负责：

1. 校验命令字段。
2. 通过 `ReferenceImageResolver` 获取参考图片。
3. 通过 `ImageToVideoSourceValidator` 校验 MiniMax 图片规则。
4. 构建 `ImageToVideoSpec`。
5. 调用 `ImageToVideoSubmissionPort` 提交供应商任务。
6. 将任务交给共享的任务协调器进行持久化和聊天投影。

### 7.2 共享任务提交协调

文生视频和图生视频的本地任务流转必须保持一致，建议抽取 `GenerationTaskSubmissionCoordinator`，统一处理：

- 创建本地 `GenerationTask`。
- 保存本地任务。
- 绑定供应商 task ID。
- 设置首次轮询时间。
- 创建 pending 聊天消息。
- 绑定聊天消息 ID。
- 提交失败时记录失败原因。

不应在一个数据库长事务中执行 MiniMax HTTP 请求。需要将状态持久化和外部请求分成可控的短步骤，保证：

- 外部请求慢时不长时间占用数据库事务。
- 提交失败时，失败任务能真实落库，不会因运行时异常回滚掉。
- 聊天消息创建失败时，任务仍有明确的可恢复状态。

## 8. 领域模型

### 8.1 公共视频参数

抽取不含生成模式的公共参数：

```java
public record VideoGenerationOptions(
        String originalPrompt,
        String submittedPrompt,
        String model,
        int durationSeconds,
        String resolution,
        boolean promptOptimizer,
        boolean fastPretreatment,
        boolean aigcWatermark
) {
}
```

### 8.2 独立 Spec

```java
public sealed interface VideoGenerationSpec
        permits TextToVideoSpec, ImageToVideoSpec {
    VideoGenerationOptions options();
    GenerationType generationType();
}
```

```java
public record TextToVideoSpec(
        VideoGenerationOptions options
) implements VideoGenerationSpec {
    @Override
    public GenerationType generationType() {
        return GenerationType.TEXT_TO_VIDEO;
    }
}
```

```java
public record ImageToVideoSpec(
        String sourceResourceId,
        VideoGenerationOptions options
) implements VideoGenerationSpec {
    @Override
    public GenerationType generationType() {
        return GenerationType.IMAGE_TO_VIDEO;
    }
}
```

`sourceResourceId` 写入 `spec_json`，用于审计、排查和任务恢复。图片字节和 Data URL 不写入任务表。

### 8.3 任务类型

`GenerationTask` 改为持有 `VideoGenerationSpec`，`generationType()` 从 spec 获取，不再固定返回 `TEXT_TO_VIDEO`。

`GenerationTaskRepositoryImpl` 根据 `generation_type` 选择反序列化类型：

- `TEXT_TO_VIDEO` -> `TextToVideoSpec`
- `IMAGE_TO_VIDEO` -> `ImageToVideoSpec`

现有 `generation_tasks` 表已有 `generation_type` 和 `spec_json`，无需为图生视频增加专用列。

## 9. MiniMax API 复用设计

### 9.1 复用策略

供应商的文生视频和图生视频均调用：

```http
POST /v1/video_generation
```

因此：

- 应用层保留独立的 `TextToVideoSubmissionPort` 和 `ImageToVideoSubmissionPort`。
- 基础设施层由同一个 `MiniMaxVideoClient` 实现两个端口。
- 请求地址、鉴权、JSON 解析、`base_resp` 错误处理和 task ID 提取只实现一次。
- 两种模式分别构建请求体，避免使用可空图片参数推断生成模式。

### 9.2 端口设计

```java
public interface TextToVideoSubmissionPort {
    String submit(TextToVideoSpec spec);
}
```

```java
public interface ImageToVideoSubmissionPort {
    String submit(ImageToVideoSpec spec, ResolvedReferenceImage image);
}
```

`MiniMaxVideoClient` 同时实现两个端口：

```java
@Component
public class MiniMaxVideoClient
        implements TextToVideoSubmissionPort,
                   ImageToVideoSubmissionPort,
                   ProviderTaskQueryPort,
                   ProviderFilePort {

    @Override
    public String submit(TextToVideoSpec spec) {
        Map<String, Object> request = commonRequest(spec.options());
        return submitRequest(request);
    }

    @Override
    public String submit(ImageToVideoSpec spec, ResolvedReferenceImage image) {
        Map<String, Object> request = commonRequest(spec.options());
        request.put("first_frame_image", ImageDataUrlEncoder.encode(image));
        return submitRequest(request);
    }
}
```

### 9.3 图生视频请求

```json
{
  "model": "MiniMax-Hailuo-2.3",
  "first_frame_image": "data:image/png;base64,...",
  "prompt": "水面缓慢流动，镜头向前推进",
  "duration": 6,
  "resolution": "768P",
  "prompt_optimizer": false,
  "fast_pretreatment": false,
  "aigc_watermark": false
}
```

### 9.4 模型与默认值

图生视频默认：

- model：`MiniMax-Hailuo-2.3`
- duration：`6`
- resolution：`768P`
- promptOptimizer：经 Skill 优化后默认 `false`
- fastPretreatment：`false`
- aigcWatermark：`false`

图生视频可用模型：

- `MiniMax-Hailuo-2.3`
- `MiniMax-Hailuo-2.3-Fast`
- `MiniMax-Hailuo-02`
- `I2V-01-Director`
- `I2V-01-live`
- `I2V-01`

文生视频与图生视频的可用模型不完全一致，由各自 Spec 或专用校验器负责模式特有校验。

## 10. 任务执行流程

```text
用户上传或选择历史图片
        |
        v
聊天请求携带 REFERENCE resourceId
        |
        v
HAssistant 识别用户要求的输出媒介
        |
        v
image_to_video(memoryId, referenceResourceId, prompt, ...)
        |
        v
ReferenceImageResolver 校验归属并读取图片
        |
        v
ImageToVideoSourceValidator 校验 MiniMax 图片限制
        |
        v
MiniMaxVideoClient 将图片编码为 first_frame_image
        |
        v
POST /v1/video_generation
        |
        v
保存 GenerationTask(IMAGE_TO_VIDEO) 并创建 pending 消息
        |
        v
复用现有轮询 -> 文件查询 -> MP4 下载
        |
        v
保存 VIDEO 资源并更新当前聊天
```

## 11. Skill 设计

新增 `optimize-image-to-video-prompt` Skill，不直接复用文生视频 Skill 的提示词规则。

图生视频提示词应主要补充：

- 图片中的主体如何运动。
- 环境中哪些元素运动。
- 镜头运动方式。
- 需要保持稳定的主体、构图和风格。
- 用户未要求时，不擅自更换主体、背景、服装或身份。

Skill 负责提示词优化和 MiniMax 参数选择，不代替模型完成 `generateImage` 与 `image_to_video` 的工具路由。

## 12. 异常与用户反馈

| 场景 | 处理 |
|---|---|
| 资源不存在或不属于当前用户 | 拒绝请求，不暴露资源是否存在 |
| 参考资源不是图片 | 返回“参考资源必须是图片” |
| 图片格式、大小、尺寸或比例不合法 | 在调用 MiniMax 前返回明确校验错误 |
| 模型、时长与分辨率组合不合法 | 在领域 Spec 构建阶段拒绝 |
| MiniMax 提交失败 | 任务记录为失败并保留错误信息 |
| MiniMax 异步任务失败 | 复用现有失败投影，更新聊天消息 |
| 轮询或下载临时失败 | 复用现有重试策略 |

## 14. 测试计划

### 14.1 参考图片解析

- 可解析当前用户新上传的图片。
- 可解析当前用户历史聊天中的图片。
- 可解析当前用户的 AI 生成图片。
- 拒绝其他用户的资源。
- 拒绝非 `IMAGE` 资源。
- 图生图改用公共解析器后行为不变。

### 14.2 图生视频领域校验

- 默认模型、时长和分辨率正确。
- 各模型的时长和分辨率组合校验正确。
- 格式、大小、短边和宽高比边界校验正确。
- `referenceResourceId` 不能为空。
- Base64 不进入 `spec_json`。

### 14.3 MiniMax 客户端

- 文生视频请求体在重构后保持不变。
- 图生视频请求体包含正确的 `first_frame_image`。
- 两种请求都使用 `/v1/video_generation`。
- MiniMax 错误码与缺少 task ID 的处理一致。

### 14.4 任务和投影

- 图生视频任务持久化为 `IMAGE_TO_VIDEO`。
- 任务能从 `spec_json` 正确恢复。
- pending、processing、materializing、succeeded 和 failed 聊天消息正确。
- 生成结果作为 `VIDEO/GENERATED` 资源回显。
- 文生视频原有测试全部保持通过。

### 14.5 Agent 与 Skill

- 参考图片 ID 会被提供给模型。
- 静态图片编辑语义使用 `generateImage`。
- 动画或视频语义使用 `image_to_video`。
- 仅分析图片时不调用生成工具。
- 图生视频 Skill 可从配置的 skills 目录加载。

## 15. 实施顺序

1. 抽取 `ReferenceImageResolver` 和 Data URL 编码器，先将图生图迁移到公共实现并保持测试通过。
2. 引入 `VideoGenerationOptions`、`VideoGenerationSpec` 和 `ImageToVideoSpec`，调整任务持久化。
3. 调整任务提交事务边界，抽取文生视频与图生视频共享的提交协调逻辑。
4. 新增图生视频 Command、UseCase、Service 和图片校验。
5. 扩展 `MiniMaxVideoClient`，完成图生视频请求提交。
6. 新增 `ImageToVideoTool`，注册到 HAssistant，并更新参考图片工具路由提示。
7. 新增图生视频 Skill 和参考资料。
8. 执行分层单元测试、持久化测试和 MiniMax 联调。

## 16. 验收标准

- 用户可上传图片后请求“让它动起来”，Agent 正确调用 `image_to_video`。
- 用户可从历史聊天中选择图片生成视频。
- 用户对参考图片请求静态修改时，仍调用 `generateImage`。
- 不允许通过构造 `resourceId` 读取其他用户的图片。
- 图片不符合 MiniMax 限制时，在提交供应商任务前返回明确错误。
- 图生视频提交后立即返回，用户可继续聊天。
- 任务完成后，MP4 自动出现在原聊天中并可预览、下载。
- 文生视频的现有接口、默认值、轮询和聊天回显行为不变。
